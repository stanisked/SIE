# SIEE: сеть Raspberry Pi 5 и Kestabor (26 октября 2026)

**Статус:** рабочая конфигурация, подтверждённая оператором в эксперименте 26 октября. Этот документ передаёт полученные результаты; изменения сетевой конфигурации не выполнялись в рамках его внесения.

## Устройства и путь подключения

| Устройство | Система и физическая сеть | Tailscale IPv4 |
| --- | --- | --- |
| Raspberry Pi 5 `piecake`, пользователь `elwis` | Ubuntu Server 24.04.5 LTS ARM64, kernel `6.8.0-1065-raspi`; `wlan0` → мобильная точка `SIE-Mobile`; LAN `10.13.32.123`, шлюз и DNS `10.13.32.108` | `100.70.100.29` |
| Ноутбук `kestabor-hn-wx9x`, пользователь `kestabor` | Ubuntu 26.04; домашний Wi-Fi или другая сеть с интернетом | `100.96.180.119` |

Оба устройства авторизованы в одной сети Tailscale. На Pi `tailscaled.service` работает и включена в автозагрузку; на ноутбуке клиент установлен, авторизован и работает. Для SSH им не требуется одна физическая Wi-Fi-сеть или подсеть. С Kestabor использовать обычный OpenSSH поверх Tailscale:

```bash
ssh elwis@100.70.100.29
```

**PASS 26 октября:** SSH-сервер Pi принял соединение, пользователь `elwis` успешно аутентифицирован; при первом соединении новый IP добавлен в `known_hosts`. Tailscale SSH не включён: `RunSSH=false`, `WantRunning=true`, `LoggedOut=false`, `CorpDNS=false`, `ControlURL=https://controlplane.tailscale.com`. DNS мобильной сети не переопределён Tailscale.

`tailscale ping 100.70.100.29` с ноутбука показал прямое соединение с `piecake`, около 129 мс в момент проверки. `tailscale status` на Pi показал:

```text
100.70.100.29   piecake          intelenge@  linux -
100.96.180.119  kestabor-hn-wx9x intelenge@  linux active; direct 192.168.0.14:41641
```

Для этого сеанса соединение было прямым, без DERP. `192.168.0.14:41641` был обнаруженным endpoint ноутбука, а не постоянным SSH-адресом. Адреса локальных сетей `192.168.0.x` и `10.13.32.x` не следует использовать как фиксированный межсетевой SSH-маршрут. Этот факт не меняет локальное подключение к ESP32 и не означает, что ESP32 доступна через Tailscale.

## Обычный порядок включения

1. Включить `SIE-Mobile`, затем Pi и дождаться Wi-Fi.
2. Подключить Kestabor к любой доступной сети с интернетом.
3. Дождаться работы Tailscale на обоих устройствах и подключиться по `ssh elwis@100.70.100.29`.

При действующей авторизации не нужно при каждой загрузке повторять `tailscale up`. Tailscale IP обычно сохраняются при смене Wi-Fi-сети; доступность проверяется в момент работы.

## Наблюдавшаяся задержка доступности

После включения Pi 26 октября ранние попытки SSH на `100.70.100.29:22` завершались `Connection timed out`; позднее доступ восстановился автоматически. Временная последовательность по журналам (MSK):

| Время | Наблюдение |
| --- | --- |
| 10:15:50 | Фактическая загрузка Ubuntu |
| +7,53 / +8,08 с | Запуск процесса `tailscaled` / переход службы в `active` |
| ≈+13 с | Подключение Wi-Fi и DHCP |
| 10:16:36 | Начальная синхронизация NTP |
| 10:32:31 | TCP read timeout к `192.200.0.106:80` |
| 10:32:32 | Tailscale сообщил о переходе на порт 443 после проблемы на порту 80; затем получил новую карту сети |
| 10:33:09 | Зафиксирован прямой контакт с другим устройством |

Повторялись `control: map response long-poll timed out!`, `control: lite map update error ... context canceled`, а после ошибки появились `controlhttp: forcing port 443 dial due to recent noise dial`, `control: netmap: got new dial plan from control`, `magicsock: new contact ... via=direct`.

**Гипотеза, не установленная причина:** периодические проблемы синхронизации Tailscale с координационным сервером через мобильную сеть, возможно связанные с TCP-портом 80. Отдельная проверка порта 80 вернула `HTTP/1.1 302 Found`; постоянная блокировка порта не подтверждена. Системное время в начале загрузки было неверным, но тайм-ауты продолжились после NTP: неверное время также не установлено как достаточная причина.

**Принятое решение:** прекратить диагностику и наблюдать. Не менять профилактически Netplan, `SIE-Mobile`, DNS, `/etc/resolv.conf`, порядок systemd-служб, Tailscale или SSH. При повторяющихся задержках более 2–3 минут при наличии интернета сравнить журналы *текущей загрузки* и последовательность событий:

```bash
tailscale status
tailscale ping 100.70.100.29
sudo journalctl -u tailscaled -b -n 60 --no-pager
systemctl status tailscaled --no-pager
timedatectl status
```

`tailscale ping` выполнять на ноутбуке. Сетевой timeout не доказывает отказ накопителя; для связи с NVMe нужны журналы. При сетевой диагностике не запускать тележку, моторы или actuator bridge. Изменять систему по одному проверяемому шагу после анализа вывода.

## Параллельный контекст NVMe

На Pi установлен Western Digital PC SN520 256 GB, ранее стоявший в ноутбуке. Для проверки влияния энергосбережения применён при загрузке `nvme_core.default_ps_max_latency_us=0`, то есть APST отключён. После перезагрузки подтверждены: применённый аргумент, PCIe Gen2 x1, чтение 1 ГиБ около 464 МБ/с без ошибок, отсутствие новых `controller is down`, reset и I/O errors в период наблюдения. SMART: `Critical Warning=0`, `Media Errors=0`, `Percentage Used=34%`.

Отключение APST оставить в силе. Первопричина прежних сбоев не доказана; период наблюдения не является гарантией общей стабильности. Без отдельной необходимости не менять настройки NVMe и не запускать интенсивные тесты накопителя.

## Границы применения

Этот сетевой handoff не активирует Measurement, управление, автономное движение и не меняет ESP32 firmware или её сетевой адрес. Для дальнейшей работы использовать актуальный SSH-адрес `elwis@100.70.100.29`; не предлагать повторную установку Tailscale или объединение устройств в одну Wi-Fi-сеть без конкретной диагностической причины. Отделять результаты эксперимента от гипотез.
